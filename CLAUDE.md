# ai-studio — правила

## Кто и что
- Владелец: Дамир. Не программист. Общение: русский, простыми словами.
- Студия делает: Android-приложения (Flutter), сайты/лендинги, позже Windows-программы (Flutter desktop).
- Задачи принимает `studio-director` (агент). Он раздаёт работу отделам из `.claude/agents/`.

## Сессии: 1 сессия = 1 проект
- Начало сессии (первый ответ): если не ясно, какой проект, спросить: «Новый проект или какой из существующих?» — список из `projects/README.md` + пункт «Офис студии». Сразу назвал проект — не спрашивать.
- Выбран проект `<slug>` → вся сессия только про него: файлы только в `projects/<slug>/` (+ `.github/workflows/<slug>.yml`, его строка в `projects/README.md`), коммиты и push только в ветку `<slug>`. Просьба про другой проект → «Открой новую сессию для <имя>», дать стартовый текст.
- Новый проект → `/new-project`, затем выдать стартовый текст для новой сессии этого проекта.
- Офис (`.claude/`, `templates/`, `scripts/`, `CLAUDE.md`, корневые README/CREDITS, `studio-check.yml`) меняем ТОЛЬКО в сессии «Офис студии». В проектной сессии — отказ: «Это правка офиса — открой сессию „Офис студии“».
- Стартовый текст сессии проекта: `Проект: <Имя> (<slug>). Ветка: <slug>. Задача: …`
- Стартовый текст офиса: `Офис студии. Ветка: ofis. Задача: …`

## Проекты
- Каждый проект — папка `projects/<slug>/`. slug = имя латиницей через дефис («Мой сайт» → `moy-sait`).
- Список проектов и этапы: `projects/README.md`. Обновлять при смене этапа.
- Новый проект — только через `/new-project` (скрипт `scripts/new_project.py`).
- Работая над проектом, трогать ТОЛЬКО `projects/<slug>/` и его workflow `.github/workflows/<slug>.yml`.
- Ветки: 1 проект = 1 ветка `<slug>` (например `moy-sait`), без `/` и без веток под каждую задачу. Офис — ветка `ofis`. Новых веток не создавать.
- Начало работы в ветке: `git fetch origin && git checkout <slug> && git pull && git merge origin/main` (свежий офис). Нет ветки → `git checkout -b <slug> origin/main`.
- `main` — общая версия. В `main` только через Pull Request из ветки проекта; после слияния ветка остаётся и работа продолжается в ней.
- Слияние в `main`: после «да» Дамира на ✅ Выпуск или на правках офиса — сливать самим (навык `merge-to-main`). Без «да» в `main` не сливать НИЧЕГО.

## Этапы (директор)
Бриф → ТЗ ✅ → Дизайн ✅ → Разработка → Тесты и ревью → Выпуск ✅.
- ✅ = стоп и ждать одобрения (навык `approval-gate`). Без «да» дальше не идти.
- Между ✅ работать самим, не дёргать по мелочам.
- Документы этапов: `projects/<slug>/docs/` (brief.md, tz.md, design.md, report.md).

## Стиль ответов (навык `kratko`)
- Без воды: без приветствий, пересказа задачи, похвал, «отличный вопрос», «если что — пишите».
- Отчёт этапа 3–5 строк: что сделано / что дальше / что нужно от Дамира.
- Код, команды, ошибки, пути — полностью и точно, не сокращать.
- Термин нужен — объяснить в 3–5 словах.

## Экономия
- Не перечитывать файлы без нужды. Читать нужные куски (offset/limit, grep).
- Простое (тексты, статус, проверки) → агенты на Haiku. Разработка → Sonnet. Директор — Sonnet. Opus — только `architect` (сложные решения: архитектура нового проекта, выбор стека) и `debugger` (непонятные ошибки). Директор зовёт их лишь когда нужно.
- Сабагенту давать короткую задачу: путь проекта, что сделать, критерий готовности.

## Безопасность
- Никаких паролей, ключей, `*.jks`, `key.properties`, `.env` в git. Только GitHub Secrets.
- Чужой код изучать во временной папке, скрипты не запускать до проверки.
- Публикация (Google Play, хостинг, merge в main) — только после ✅.

## Проверка перед «готово»
- Проверки GitHub Actions агенты смотрят сами: `python3 scripts/ci_status.py` после push. Дамира не просить запускать проверки вручную.
- Flutter: `flutter analyze` и `flutter test` в папке проекта — без ошибок (локально или в CI через `ci_status.py`).
- Сайт: открывается, адаптив 360px/1280px, форма работает, нет ошибок в консоли.
